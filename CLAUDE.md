# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

A local pipeline that watches permitted streamers playing GTA 6 (Grand Theft Auto VI), spots viral moments while they're live, and hands those moments to **Clips Kitty** (`ColinGPT9/clips-studio`, a desktop app the owner installs separately) to be cut into vertical YouTube Shorts. A human approves every clip before it is published.

**This repo is the orchestrator around Clips Kitty, not a clip editor.** Clips Kitty does the transcription, choosing the exact clip boundaries, the gaming layout (webcam + game), captions, titles/descriptions/hashtags, rendering and the YouTube upload. This repo does what Clips Kitty can't: the permission gate, live GTA 6 category watching, rolling recording, per-channel chat and audio spike detection, the spoiler queue, mandatory credit lines, and the approve-before-publish rule.

## Target machine

The owner runs this on **Windows with an NVIDIA GPU**, with Clips Kitty installed and set to use the **Claude API** (configured in Clips Kitty: Settings → AI). Development happens in a Linux cloud container where Clips Kitty isn't running, so:
- Use `pathlib`. Call `subprocess` with argument lists and `shell=False`. Don't use POSIX-only APIs (`fork`, `killpg`, sending SIGTERM to process groups). Stop children with `proc.terminate()`, and on Windows create them with `CREATE_NEW_PROCESS_GROUP`. Keep the default Proactor event loop.
- All Clips Kitty access goes through `gta6clips/clipskitty/client.py`. Tests run against `tests/fake_clipskitty.py`, a FastAPI stub that copies the documented responses. Real integration runs happen on the owner's PC.
- streamlink, yt-dlp and chat-downloader come from pip, inside the venv. ffmpeg for recording is a system dependency: ask before `winget install`, or point `config.yaml → paths.ffmpeg` at a portable build. Clips Kitty ships its own ffmpeg, but don't depend on its install path.

## Hard rules (owner requirements, do not relax)

- **Permission gate:** only channels with `permission: true` in `streamers.yaml` may be recorded, downloaded, sent to Clips Kitty or published. Enforce this in one function (`gta6clips/streamers.py`) that every entry point calls, and keep a test for it.
- **Nothing is published without approval.** Only clips with our status `approved` are published. Always send `privacy: "private"`, or a `publish_at` (which YouTube forces to private). Never rely on Clips Kitty's publish defaults, which can be `public`. After an upload, compare `privacy` against `actual_privacy`.
- **Clips Kitty's own automation stays off.** That means watched channels (`/automation`) and any auto-publish settings. Our orchestrator is the only thing that queues jobs and publishes. On startup, check `GET /automation` and `GET /settings` and refuse to run if either is on.
- **Credit is mandatory.** Every description includes the streamer's `credit` line and channel URL from `streamers.yaml`. We write it with `PATCH /clips/{id}`, and the publish step re-checks it and refuses if it's missing.
- **Spoilers** (major story missions, the ending) get our status `spoiler_hold` and show in a separate Spoilers tab. They are never in the main queue.
- Secrets live only in `.env`, which is gitignored. `streamers.yaml` is edited by the owner. Don't rewrite their entries.
- Ask the owner before installing anything system-wide. Installing into `.venv` is fine.
- Resolve the Twitch GTA 6 game ID at runtime (Helix `GET /games?name=Grand Theft Auto VI`) and cache it. Don't hardcode it.
- Clips Kitty is AGPL-3.0. Integrate with it over its HTTP API and plugin contract only. Don't copy its source into this repo.

## Architecture (planned)

```
watcher → recorders (+ chat) → spike detector → window cutter → Clips Kitty → post-processor → review → publish (via Clips Kitty)
```

- **The state lives in our own SQLite (`data/orchestrator.db`).** We never write to Clips Kitty's database; we only use its API. The tables are `streams`, `segments`, `chat_messages`, `signals`, `windows` (moments sent to Clips Kitty, with `ck_video_id`/`ck_job_id`) and `clips` (Clips Kitty clip ID plus our status: `pending_review | spoiler_hold → approved | rejected → published`), and `publish_log`.
- **A single clock.** Segments, chat and audio levels are all stored in wall-clock UTC. Segment files are named after their start time in UTC epoch seconds. VOD mode builds the same timeline from the VOD's start time.
- **Platform order: YouTube Live first** (the first streamer is `@TheBurntPeanut` on YouTube), then Twitch, then Kick. On YouTube, don't poll `search.list` for live status: it costs 100 units per call, which blows the 10,000/day quota at a 2–3 min interval. Instead, check `<channel>/live` with yt-dlp, which costs no quota. The Data API doesn't expose the game, so detect GTA 6 from the stream title and description keywords, with yt-dlp metadata where available. Make the keywords configurable.
- **watcher:** a single-threaded loop (`live/watcher.py`; children run as processes, so nothing blocks long) that polls every `live.poll_seconds` (150 s); YouTube via yt-dlp `<channel>/live`, Twitch later through Helix. It starts a recorder when a permitted streamer is live in the GTA 6 category and stops it when they leave the category. Concurrency is capped by `max_concurrent_streams` (default 3, ordered by `priority`). A `platforms/` adapter leaves room for YouTube Live and Kick. (Clips Kitty's own watchers only pick up *finished* VODs, which is why this is ours.)
- **recorder:** ffmpeg reads the HLS playlists that yt-dlp resolves (video + audio, `-map 0:v:0 -map 1:a:0`) and writes `-c copy -f segment -segment_time 60` MPEG-TS pieces, supervised and restarted with backoff and a fresh URL. This replaced the planned streamlink pipe because it was already proven on this PC; streamlink isn't a dependency. A janitor deletes segments older than `retention_hours`, except those that an unsent or in-progress window still references.
- **spike detector:** cheap, with no transcription or LLM. Chat velocity, keyword hits (`CLIP IT`, `KEKW`, `?????`…) and audio loudness are each z-scored against **that channel's rolling baseline**, then combined with the weights in `config.yaml → scoring.weights`. Spikes that overlap are merged before anything is sent.
- **window cutter → Clips Kitty:** concatenates the segments for `[spike − lead_in, spike + tail]` (about 2–4 min, so the clip gets 30–60 s of lead-up) into an mp4. It then calls `POST /videos/local` with the gaming options, `channel=<streamer>`, a small `max_clips`, a GTA-specific `focus` text (ragdolls, police chases, NPCs, glitches, rage, stunts, first reactions, one-liners), and a `webhook_url` pointing at our local listener. Clips Kitty runs **one job at a time**, which is why our windows are short and the queue is prioritized.
- **Moment finding uses the official GTA plugin** `colingpt9/gta-vi-highlights` (MIT, local, `network: []`, `sends: []`), which the owner installs from Clips Kitty's Marketplace. Every job sends `pipeline: {"id": "colingpt9/gta-vi-highlights", "version": <config.yaml → clipskitty.gta_plugin_version>}`, pinned at `0.4.1` (commit `f1176c6`), and it needs Clips Kitty 2.1.0 or later. Before raising the pin, re-review the plugin's diff, because plugins aren't sandboxed. If the plugin isn't installed, Clips Kitty refuses the job with a message naming the plugin. Show that to the owner rather than silently dropping `pipeline`. Its author says it is **not validated on GTA VI gameplay** and only labels physical events (chases, crashes) from transcript cues, so our chat and audio spikes stay the main reason a window is sent. It finds nothing in moments that are funny because of what he says, so live windows it finds nothing in fall back once to Clips Kitty's own finder (see Status).
- **Our own rater plugin (Phase 2, optional):** a local plugin (`plugins/gta6-signals/`, with `inputs: [moments, transcript]` and `outputs: [ratings, context]`) that sends our chat and audio scores through `rate`, on top of the GTA plugin's finds. It must declare `network: []` and `sends: []` honestly.
- **post-processor:** on the webhook, reads `GET /videos/{id}/clips` and the captions, runs the spoiler check (Claude, through `gta6clips/llm/`), writes 3 title options, and sets the description (credit line + link) and hashtags (`#GTA6 #GTAVI #Shorts #<streamer>`) through `PATCH /clips/{id}`.
- **review:** our FastAPI page on `127.0.0.1` (not Clips Kitty's port, 8765). It previews clips through Clips Kitty's `/media/{clip_id}`, lets the owner approve, reject or pick and edit a title, and has a Spoilers tab. Fine edits happen in the Clips Kitty studio.
- **publish:** `POST /clips/{id}/publish` with an explicit private or `publish_at`. Clips Kitty's `quota` counts uploads (since June 2026, `videos.insert` has its own bucket of 100 per day per project). We warn at `youtube.quota_warn_at` and stop at the limit, but a 403 from YouTube is the real answer.

## Clips Kitty API notes

- The owner has the **Microsoft Store** build. Its data folder is `%LOCALAPPDATA%\Packages\ClipsStudio.ClipsStudio_<id>\LocalCache\Local\Clips Studio\data`, not the winget path `%LOCALAPPDATA%\Clips Studio\data`. Find it with a glob on `ClipsStudio.ClipsStudio_*`. Plugin routes need the `X-Clips-Kitty-Session` header, read from `<data>\plugins\session.secret`.
- Clips Kitty 2.1.0 doesn't bundle the official GTA plugin in its catalog (it was listed after the release), and the online list never adds the project's own listings. Until a newer release bundles it, install it by Git address through `POST /plugins/plan` + `/plugins/install`.
- **2.1.0 also rejects the plugin's `twitch.context.read` permission** ("unknown permission"). Every plugin version asks for it, but only unreleased Clips Kitty knows it. Workaround in use: a local copy of plugin commit `f1176c6` in `%USERPROFILE%\ClipsKittyPlugins\`, with only `twitch.context.read` removed from `clipskitty.yaml`, installed with `{"kind": "folder"}`. The plugin's Twitch use is optional (report metadata, read through `getattr`), and 2.1.0 ships SDK 1.3.0, which is what the plugin needs. Its ID and version are unchanged, so the job's `pipeline` ref still matches. Once a Clips Kitty release knows the permission, reinstall the unmodified plugin from Git.
- `http://127.0.0.1:8765`, with **no authentication**. Address it only as `127.0.0.1`/`localhost` (other `Host` headers get a 400), and never expose it.
- **The split layout (game + creator) needs a person on camera.** Clips Kitty's webcam detection finds people only ("an avatar is never taken for the streamer"). The Burnt Peanut streams as an animated peanut avatar, so the Phase 1 clips came out game-only (`render_opts.gaming.layout: "fill"`, `used_cam: null`; the log says "no webcam found"). Fix: the owner draws the avatar box once in Clips Kitty's Gaming layout editor and ticks "Remember for this creator's next videos". Clips Kitty names that creator `TheBurntPeanut` (its @handle), and `/videos/local` matches creators by `channel`, so `scan` sends `Streamer.clipskitty_creator` (the handle, or `clipskitty_creator` in streamers.yaml), not the display name. The creator-layout routes (`/clips/{id}/creator-gaming-layout`) are internal: don't call them. Done and verified 2026-11-18: the box is saved for TheBurntPeanut, and a 3-min recording of his live GTA 6 stream sent as `channel: TheBurntPeanut` rendered split ("Gaming: using the split saved for this creator", `by: "creator"`, preset `circle_cam`), with the peanut in frame. Re-rendering a clip gives it a new id (clip 1 → 10), so Phase 4/5 must follow `clip_replaced`.
- A clip's `path` from the API is the unvirtualized `%LOCALAPPDATA%\Clips Studio\...`. On the Store build the file is really under `Packages\ClipsStudio.ClipsStudio_*\LocalCache\Local\Clips Studio\...`, so use `/media/{clip_id}` rather than the path.
- YouTube live offers only separate video and audio HLS formats (no combined format), so a Phase 3 recorder must merge two inputs (streamlink does this itself).
- `POST /jobs` and `/videos/local` return `{"job_id": null, "already_processed": true}` for repeats. Check for a null `job_id` instead of assuming a job was created. A 409 means the queue is full.
- Use only the endpoints that `docs/API.md` (in the clips-studio repo) marks as supported. Record the Clips Kitty version we tested against in `config.yaml → clipskitty.tested_version`, and log a warning if `GET /health` reports another version.

## Code map

- `gta6clips/streamers.py`: streamers.yaml loading and **the permission gate** (`require_permission`, `permitted_streamer_for`). `permission` must be a real YAML boolean.
- `gta6clips/clipskitty/client.py`: the only Clips Kitty HTTP code. `readiness.py` refuses to start when automation or auto-upload is on, a blocking preflight check fails, or the GTA plugin is missing, off, or not at the pinned version.
- `gta6clips/vod.py`: Phase 1 flow (probe → gate → readiness → `POST /jobs` with `gaming`, the pinned `pipeline`, `focus` and required `hashtags` → poll → post-process). `resume_job` collects `--no-wait` jobs, but only ones in our `windows` table.
- `gta6clips/postprocess.py`: credit block (idempotent, re-checked with `has_credit`), hashtag merge, Claude titles, `PATCH /clips/{id}`, and the `clips` row as `pending_review`. Clips already tracked are skipped (no repeat Claude calls). Approved, rejected and published clips are never touched.
- `gta6clips/llm/titles.py`: `ClipsKittyTitles` (default, free) or `ClaudeTitleWriter`, picked by `cli.make_title_writer` from `llm.enabled`. Claude (`claude-opus-5-5`, effort from config) with JSON-schema structured output and `fallbacks: "default"` (beta `server-side-fallback-2026-07-01`). All prompts live in `gta6clips/llm/`.
- `gta6clips/scan.py`: Phase 2 flow (probe → gate → GTA title check → refuse live → readiness unless `--dry-run` → chat + loudness, cached in `streams`/`chat_messages`/`signals` → `scoring` → windows (`planned → submitted → done → collected`, or `failed`) → cut → `/videos/local` with `windows.max_clips` → wait → post-process with chat around each clip). Reruns don't send anything twice: they reuse signals, retry `planned`/`failed` windows and collect `submitted` ones.
- `gta6clips/live/`: Phase 3. `youtube.py` (`check_youtube_live`: live/offline/unknown, an unknown never stops a recording; `resolve_stream_urls`), `recorder.py` (`SegmentRecorder`: pieces renamed to their UTC start, the run's clock anchored on the first piece's mtime; `cut_segments`: concat → mp4), `chatfeed.py` (yt-dlp live chat subprocess, tailed with `chat.ChatFileTail`, raw files deleted at stop), `select.py` (`LiveSelector`, pure, replayable on a VOD), `session.py` (one stream: ingest → score the last 25 min → decide → cut → window `planned` with `local_path`; stored as a stream with video_id `<id>@<origin epoch>`), `dispatch.py` (sends planned live windows strongest first, polls jobs without blocking, post-processes, re-checks readiness every 10 min), `watcher.py` (who's live, sessions, janitor), `factory.py` (real sessions).
- `gta6clips/twitch.py` (`Helix`: app token from `TWITCH_CLIENT_ID/SECRET`, renewed once on a 401; `game_id` cached in the `kv` table; `user_ids`; `clips`) and `gta6clips/twitch_clips.py` (`TwitchClipSource`: permitted Twitch streamers' most-viewed GTA 6 clips of the last `twitch_clips.hours`, cut from the VOD with lead-in/tail (or the clip itself without a VOD, or when the VOD can't be downloaded; a clip with a VOD but no `vod_offset` yet waits up to 3 h), deduped by clip URL and by overlapping VOD range, skipped under `twitch_clips.min_score` (60, the review score `scoring.review_score`; exact-moments clips are scored from our window score, since that plugin returns a flat 90), queued as `planned` windows with `finder: clipskitty` and a per-window `focus` naming the clipped range, on a stream `<login>@clips` so the watcher's dispatcher sends and collects them). `watch` runs it every `twitch_clips.every_minutes` when a permitted Twitch streamer and the keys exist; `twitch-clips [--dry-run]` runs it once.
- `gta6clips/compilation.py` + `gta6clips/llm/fails.py` (2026-11-24, the owner pays for the API for this): `Compiler` checks each clip of `compilations.streamers` once (`fail_checks` table) with `ClaudeFailJudge` (`claude-haiku-5-5`, effort low, 8 frames from the window recording at 640 px + transcript + chat, JSON schema), then `plan_parts` (strongest distinct fails ≥ `min_strength`, ≤ `max_fails`, each ≤ `max_part_seconds`; over `max_seconds` the weakest go down to `min_fails`, then all are shortened evenly), `stitch` (ffmpeg, re-encoded to 1920x1080/30 fps), and a planned window on stream `<handle>@compilations` with `finder: exact` over the whole file (`compilations` table). The dispatcher sends it like a live window (no edge/length checks), and `compilation_title_writer` (Opus) writes title, hook and description from `parts_context`. `drop` rejects the made clip and rebuilds. `gta6clips/crash_hunt.py` (`hunt`): `crash_candidates` scores the VOD's chat replay (cached by `scan._load_chat`) for crash words + laughs in 10 s bins, `frames_from_url` reads frames with ffmpeg from the 360p stream URL (one yt-dlp lookup per VOD, no download), verdicts go to `vod_fails` (keyed by video and chat peak); `Compiler.build(include_vods=True)` downloads chosen ones in HD (`fetch`, `HD_PAD_S` each side, 10 s apart) and labels them `v<id>`. `hunt` refuses while a recording is running (bot-flag risk). The judge also returns `impact_s` (the crash's own second): parts are cut `before_impact_seconds`/`after_impact_seconds` around it (`part_range`); without it, the end of the marked stretch. Haiku's stretches ran up to 55 s, so cutting from their start missed the crash (2026-11-24). `compile --refine` looks again at old fails, `--unbuild ID` takes a compilation back, `--top 5 --shorts 3` builds the Top 5s. Per-clip titles stay Clips Kitty's (`llm.enabled: false`).
- `hold_uploads_while_live` (streamers.yaml, per streamer): `PublishService._why_not` refuses an upload while `is_live` (a `twitch.TwitchLiveCheck`, cached 2 min) says live or can't tell; `watch` runs `PublishService.upload_held` every 10 min when `publish.auto_schedule` is on. CaseOh has it, at the owner's request.
- `gta6clips/review/`: Phase 4. `service.py` (`ReviewService`: cards per tab, approve/reject/undo/set_title, `reconcile` for re-rendered clips; raises `ReviewError` with a message for the owner), `app.py` (FastAPI; loopback Host only, POSTs must be JSON and same-origin; one shared sqlite connection behind a lock, opened with `db.connect(..., threads=True)`), `page.html` (the whole UI, vanilla JS).
- `gta6clips/publish/`: Phase 5. `schedule.py` (`SlotSettings`, `next_slots`, RFC 3339 with offset), `service.py` (`PublishService`: `status`, `plan`, `execute`, `schedule_one`, `refresh`, `upload_for`). The review page's Approved tab drives it through `/api/publish/{status,plan,execute}`; with `publish.auto_schedule` the approve route also calls `schedule_one` (the approval stands if scheduling fails). `youtube_direct.py`: channels in `publish.channels` besides Clips Kitty's one (a streamer's `youtube_channel` picks one; '' = Clips Kitty's). The owner's OAuth client JSON at `secrets/youtube_client.json`; `connect-youtube <key>` (PKCE, loopback redirect, refuses a channel whose handle isn't the configured one) saves the refresh token DPAPI-encrypted at `secrets/youtube_<key>.token`; `DirectUploader.upload` downloads `/media/{id}`, does a resumable `videos.insert` that's always private + `publishAt`, and the row is settled at once (`publish_log.channel` = key). Slots are taken per channel; the upload count adds our direct uploads to Clips Kitty's (same Google Cloud project).
- `gta6clips/notify.py`: Discord webhook notifications (`DISCORD_WEBHOOK_URL` in `.env`, `notify:` in config). `notify.setup(cfg)` in `cli.main`; `notify.current()` is called for new clips (dispatcher), stream start/stop (session) and uploads (publish); a `_ProblemHandler` on the `gta6clips` logger forwards WARNING+ as problems, deduped per `problem_repeat_minutes`. Sends never raise; `allowed_mentions` is empty. Verified with `notify-test` on the owner's server (2026-11-19).
- `plugins/exact-moments/` (`gta6clips/exact-moments` 1.0.0, ours, `inputs: [transcript]`, `outputs: [ranges]`, `permissions: [transcript.read]`, `network: []`, `sends: []`): a finder that returns the ranges in its `ranges` setting ("33.0-87.0"), ends snapped to sentence breaks (`src/ranges.py`, pure, tested from `tests/test_quality.py`). Installed with `POST /plugins/plan` + `/plugins/install` `{"kind": "folder"}`. `gta6clips/exact.py` (`ExactSettings.pipeline`). Windows carry `moment_start_s`/`moment_end_s` (seconds of the cut) and `finder: exact`; the dispatcher then sends this plugin as the pipeline with `max_clips: 1`. Verified 2026-11-20: CaseOh's 135 s recording asked for 33-117 s gave an 87 s split clip (the finders had given 15-26 s). 1.1.0 (2026-11-22) also has `outputs: [ranges, context]`: its `notes` setting (`||`-separated) becomes `job.understand` notes, which Clips Kitty gives the AI that writes titles; `exact.twitch_notes` (the viewers' clip title) and `exact.chat_notes` (most repeated live chat lines, laughs left out) fill it. Clips are tight since 2026-11-22 (Studio: ~60% swiped away, almost no Shorts-feed views): pad 2 s, live 30 s before / 8 s after the peak, `qa.min_seconds` 15.
- Quality check (`live/dispatch.py`: `QualitySettings`, `quality_problems`, `Dispatcher._check_quality`, config `qa:`): after post-processing, a clip under `qa.min_seconds` or within `edge_seconds` of the recording's edge is sent back once wider (`_send_wider`: copy to `<stem>_wide1`, window back to planned, old clip rejected with a note); one with layout other than `split`, or still failing, becomes `needs_fix` (`db.REVIEW_MOVES`). Sound: `media.silent_stretch` (volumedetect in 8 s chunks, silent under -70 dB; Twitch-muted VOD audio reads -91 dB) is used by `TwitchClipSource._queue` (a muted VOD cut falls back to the clip itself, which keeps its sound: seen 2026-11-20 on xQc's club clip) and by the check (silent stretch → `needs_fix`). The review page's Needs a fix tab: `ReviewService.rerender` (copy to `<stem>_fixN`, window planned, old clip rejected; only `@` streams, which the watcher sends) and `send_to_review`.
- `gta6clips/scoring.py`: pure functions. 5 s bins, centred smoothing, robust z against the trailing 10 min (median/MAD; counts floor the spread at √median), positive z weighted and re-normalised over the signals present, runs over threshold → one spike at the peak, windows merged strongest-first up to `windows.max_seconds`.
- `gta6clips/chat.py`: YouTube chat replay parsed from yt-dlp's `live_chat` track. We chose this over chat-downloader (unmaintained since 2023) for YouTube. Twitch/Kick chat isn't supported yet, so those VODs score on audio only.
- `gta6clips/downloads.py`: `YtDlpFetcher` (chat, audio, `download_ranges` cuts), each method gated with `require_permission`. Tests use a fake `Fetcher`. `gta6clips/media.py`: `find_ffmpeg` (`paths.ffmpeg` or PATH) and ebur128 loudness.
- `gta6clips/spoilers.py`: `KeywordSpoilerCheck` (free): `spoilers.keywords` in the stream title, clip title or transcript, or `chat_min_hits` spoiler messages in chat within 30 s of the clip → `spoiler_hold`. A Claude check would plug in through the `SpoilerCheck` protocol (needs the owner's OK, since it needs the key).
- `tests/fake_clipskitty.py`: the 2.1.0 API stand-in. Extend it whenever the client uses a new endpoint, copying shapes from the 2.1.0 `docs/API.md`, not from `main`.
